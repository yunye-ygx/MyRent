# AI Recommendation V2 Design

Date: 2026-04-28

## Background

The current AI rental assistant has shipped a minimum closed loop:

- the frontend can start a dedicated AI recommendation conversation
- backend state is stored in Redis
- Spring AI calls a compatible LLM
- the LLM currently returns structured slots, a reply, and an action-like decision
- backend may call the existing `smartGuide` recommendation capability when required slots are present

This version is usable, but its boundaries are still too loose:

- prompt content is hardcoded in Java
- the model still returns workflow decisions such as `ASK`, `ADVISE`, and `SEARCH`
- prompt context currently depends too heavily on raw conversation history
- state persistence mixes multiple responsibilities and stores more than the model actually needs at runtime

The next iteration should keep the existing product surface but upgrade the architecture so the AI module is easier to understand, safer to evolve, and more representative of real project-grade AI integration.

## Confirmed Product Decisions

The following decisions are fixed for this iteration:

1. Prompt content must be moved out of Java source code.
2. Prompt files must live under `src/main/resources/prompts/ai-recommend/`.
3. The LLM must no longer return workflow decision fields such as `ASK`, `ADVISE`, or `SEARCH`.
4. The LLM should continue to generate natural-language reply text.
5. Backend code must own the workflow decision and final execution path.
6. Conversation history remains valuable and must be kept.
7. The model must not receive the full stored history on every turn.
8. Model context should be built from:
   - current slots
   - backend-generated summary
   - recent conversation window
   - current user message
9. The recent conversation window sent to the model is the latest 6 turns.
10. Redis should retain the latest 30 turns as raw history.
11. Conversation summary should be generated by backend rules, not by another model call.
12. This stage is design-only; no implementation or commit is part of this spec itself.

## Goals

- Remove hardcoded prompts from `SpringAiRecommendDecisionClient`.
- Redefine the LLM role so it focuses on language understanding and reply generation.
- Move workflow decision authority fully into backend orchestration.
- Reduce prompt token waste by avoiding full-history prompt construction.
- Preserve enough context to support multi-turn follow-up understanding.
- Keep the current product behavior familiar to users while improving architecture.

## Non-Goals

- No model provider switch in this iteration.
- No new database table.
- No vector database or RAG layer.
- No streaming response redesign.
- No change to the public user-facing route structure.
- No conversion into a fully autonomous tool-calling agent.
- No removal of Redis state persistence.

## Core Architectural Change

The current implementation behaves like:

1. load state
2. append user message
3. send slots + raw history + user message to the model
4. receive `action + reply + slots`
5. backend validates or overrides the action
6. backend may call `smartGuide`

The new implementation should behave like:

1. load state
2. append user message into raw history
3. build prompt context from:
   - current slots
   - backend summary
   - recent 6 turns
   - current user message
4. send context to the model
5. receive only `slots + reply`
6. backend merges and normalizes slots
7. backend decides whether the turn is effectively:
   - `ASK`
   - `ADVISE`
   - `SEARCH`
8. backend decides whether `smartGuide` should run
9. backend may override the model reply if it conflicts with the true backend decision
10. backend stores updated slots, summary, and raw history

This is the central design principle for V2:

- the model owns language interpretation and wording
- backend owns workflow truth and execution truth

## Prompt Externalization Design

Prompt files should be split by responsibility instead of kept as a single large text block.

Recommended directory:

```text
src/main/resources/prompts/ai-recommend/
  system.txt
  user-context.txt
  output-format.txt
```

### `system.txt`

Responsibility:

- define the assistant role
- define hard constraints
- define truthfulness boundaries
- define that the model is not the workflow decision maker

This prompt must explicitly instruct the model:

- extract slots from user input and available context
- generate a helpful natural-language reply
- never claim to have queried real houses on its own
- never fabricate listings
- never output workflow decision fields

### `user-context.txt`

Responsibility:

- define how runtime context is organized before being sent to the model

This template should include placeholders for:

- current structured slots
- backend-generated summary
- recent 6 turns
- current user message

### `output-format.txt`

Responsibility:

- define the exact output contract expected from the model

Recommended output contract:

```json
{
  "reply": "string",
  "slots": {
    "city": null,
    "locationName": null,
    "budgetYuan": null,
    "budgetScope": null,
    "rentMode": null,
    "priority": null,
    "preferences": []
  }
}
```

No `action` field should remain in the model contract.

## Prompt Loading Strategy

Prompt externalization must not introduce per-request file IO.

Required runtime behavior:

- prompt files are loaded once at application startup or lazily loaded once and cached in memory
- every request reuses in-memory prompt content
- runtime request handling only performs variable interpolation and string assembly

This keeps prompt content maintainable without introducing meaningful runtime IO overhead.

## LLM Role Redefinition

The current `SpringAiRecommendDecisionClient` behaves like a decision client. In V2 it should conceptually become a language extraction and reply client.

The LLM should be responsible for:

- interpreting natural-language user intent
- mapping utterances into structured slot updates
- producing a concise assistant reply aligned with the visible conversation

The LLM should not be responsible for:

- deciding whether backend search actually runs
- deciding whether a reply is classified as `ASK`, `ADVISE`, or `SEARCH`
- deciding whether a result is valid for `smartGuide`
- determining business truth about readiness

## Backend Decision Rules

Backend should own the effective turn decision after slot merge and normalization.

### Required Slots for Search

For this iteration, the backend remains authoritative that real search can run only when all of the following are usable:

- `budgetYuan`
- `rentMode`
- `locationName`

### Effective Decision Rules

Backend should derive an effective action using deterministic rules:

1. `SEARCH`
- all required slots are usable
- backend query preconditions are satisfied

2. `ASK`
- one or more required slots are still missing or invalid

3. `ADVISE`
- search should not run yet
- but the assistant can still provide exploratory guidance
- this is a backend-selected fallback state, not a model-selected state

### Reply Conflict Resolution

Because the model still generates reply text, backend must be able to override or replace that reply when it conflicts with true backend state.

Examples:

- if the model says it will start searching, but backend still lacks `rentMode`, backend must replace the reply with a follow-up question
- if the model implies real listings were found before `smartGuide` runs, backend must replace the reply
- if `smartGuide` fails, backend must replace the reply with a safe fallback advisory message

This means reply generation remains model-driven, but reply acceptance remains backend-controlled.

## State Storage Design

Redis state should be split by responsibility instead of storing a monolithic session object plus duplicate history payloads.

Recommended keys:

- `ai:recommend:slots:{userId}`
- `ai:recommend:history:{userId}`
- `ai:recommend:summary:{userId}`

### Stored Data

#### Slots

Stores the current structured state:

- `city`
- `locationName`
- `budgetYuan`
- `budgetScope`
- `rentMode`
- `priority`
- `preferences`

#### Raw History

Stores the latest 30 turns as archival conversation evidence.

Each history item should remain lightweight:

- `role`
- `content`
- optional metadata only if already justified by existing code

#### Summary

Stores backend-generated compressed context for the model.

Summary should not be a vague paragraph. It should be a compact, structured memory string or structured object that covers:

- confirmed city
- confirmed location
- confirmed budget
- confirmed rent mode
- current preference priority
- recent notable preferences
- currently missing required slots

## History and Summary Runtime Policy

The system should separate what is stored from what is sent to the model.

### Stored in Redis

- latest 30 turns raw history

### Sent to the Model

- backend summary
- latest 6 turns
- current slots
- current user message

This achieves the desired balance:

- long-term context is preserved in Redis
- prompt cost remains bounded
- summary provides continuity beyond the 6-turn model window

## Summary Generation Strategy

Summary must be generated by backend rules rather than by another model call.

This keeps the system:

- deterministic
- cheaper to run
- easier to test
- easier to debug

The summary generator should derive its content from:

- merged current slots
- current missing slot list
- selected recent conversation hints that are not yet formal slots

If a preference is already represented in slots, summary should not duplicate it excessively.

## API Contract Direction

The frontend-facing response can continue to include an `action` field for rendering and UI control, but that field becomes a backend-generated field rather than an LLM-generated field.

Recommended page-facing response continues to contain:

- `sessionId`
- `action`
- `assistantReply`
- `slots`
- `missingSlots`
- optional `recommendation`

The internal model-facing response should shrink to:

- `reply`
- `slots`

## Current Class-Level Refactoring Direction

### `SpringAiRecommendDecisionClient`

Should be refactored to:

- load prompt content from resource files
- build prompt context from `slots + summary + recent 6 turns + user message`
- parse a model response containing only `reply + slots`

Its current decision-oriented naming may become misleading, so rename or role-adjustment should be considered during implementation planning.

### `AiRecommendServiceImpl`

Should become the clear workflow orchestrator:

- append user turn
- call AI extraction/reply client
- merge and normalize slots
- generate missing slots
- derive backend action
- conditionally call `smartGuide`
- decide final assistant reply
- append assistant turn
- rebuild and save summary

### `RedisAiRecommendStateStore`

Should be redesigned to:

- store slots independently
- store raw history independently
- store summary independently
- stop persisting redundant overlapping payloads

## Failure Handling

The following failure rules should be explicit in implementation:

1. If model invocation fails:
- use backend fallback reply
- preserve session continuity
- do not pretend search happened

2. If model output is malformed:
- ignore unusable fields
- keep prior slots where possible
- use backend fallback reply

3. If model reply conflicts with backend action:
- backend reply override wins

4. If `smartGuide` fails:
- effective action becomes `ADVISE`
- return a fallback reply that does not claim successful house retrieval

## Observability Requirements

This iteration should improve inspectability of the AI pipeline.

Recommended logging targets:

- input user message
- current slots before model call
- summary used for model call
- recent history size sent to the model
- raw model output or parsed result
- merged slots after normalization
- backend-derived action
- whether `smartGuide` executed

This is important because once workflow decision moves fully into backend logic, debugging should make it clear whether an issue came from:

- slot extraction
- slot normalization
- backend readiness rule
- search execution
- reply override logic

## Testing Strategy

### Backend Tests

Add or update tests for:

1. prompt loading from resource files
2. model contract parsing without `action`
3. backend derivation of `ASK` when required slots are missing
4. backend derivation of `SEARCH` when required slots are present
5. backend downgrade or reply override when model wording conflicts with true state
6. summary generation correctness
7. history trimming to 30 stored turns
8. model input trimming to recent 6 turns
9. state store persistence for `slots`, `history`, and `summary`

### Regression Focus

Existing scenarios such as:

- city-only input
- budget plus location but no rent mode
- explicit `整租` or `合租`
- search-ready input
- exploratory advice request

must continue to behave correctly after the LLM `action` field is removed.

## Risks and Trade-Offs

### 1. Model Reply Without Action Signal

Once the model no longer returns `action`, backend must be more careful to classify state correctly. This increases orchestration responsibility but improves correctness and control.

### 2. Summary Quality

If backend summary is too sparse, the model may lose useful long-range context. If it is too verbose, token savings decrease. The summary format should therefore stay compact and structured.

### 3. Reply Override Frequency

If the model often produces replies inconsistent with backend truth, too many overrides may reduce perceived conversational naturalness. Prompt wording must therefore strongly communicate the model's non-execution role.

### 4. Naming Drift in Existing Classes

The current naming still reflects a decision-first architecture. The implementation plan should address whether to preserve compatibility first or rename components for conceptual clarity.

## Success Criteria

This V2 design is successful when:

- prompt content is no longer hardcoded in Java
- runtime prompt loading does not perform per-request file IO
- the model no longer returns `ASK`, `ADVISE`, or `SEARCH`
- backend becomes the only authority for workflow decision
- Redis retains useful history while model prompt input is capped to 6 recent turns
- summary is generated by backend rules and used in prompt context
- the assistant still feels natural because the model continues to generate reply text
- real house search remains grounded in backend `smartGuide`, not in model claims
